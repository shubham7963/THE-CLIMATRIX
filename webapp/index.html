02 Methodology

Pipeline

  1. Daily climate data per city, 1991–2026 (36 years × 8 cities)
  2. Feature engineering: day-of-year → sin/cos cyclical encoding + year
  3. Random Forest Regressor per city per target (temp, rainfall, humidity, wind)
  4. Forward hold-out validation (train ≤2018, test 2019–2026)
  5. Backend loads the trained models directly and runs live inference per request
  6. Risk tier = extrapolation distance + local historical volatility
  7. Insight engine narrates the numeric output in plain language

Limitations

  • Training data is representative (built from published climate normals + realistic daily variability + trend), not live satellite data. A NASA POWER fetch + validation script pair is included in /scripts to check against, or swap in, real data.
  • This is a climatological risk projection, not day-specific weather — no model can reliably forecast exact conditions for one calendar day more than ~10–14 days out.
  • Rainfall R² is modest (0.17–0.35), consistent with rainfall's genuinely high day-to-day randomness even in real climate data. A two-stage model (rain probability × expected amount) is used instead of a single regressor, giving a more informative "chance of rain" output even though it doesn't change the underlying difficulty.
  • Risk tiers reflect general seasonal instability, not discrete extreme events (cyclones, sudden heatwaves).

About CFDS–RAS

        
What this system does, where the data comes from, and how the numbers on the other pages are actually produced — written for anyone, not just the technical reviewer.

      


      
01 What this is

      

        

          CFDS–RAS is a decision-support tool: pick a city and a future date, and it
          gives you a data-driven expected climate range (temperature, rainfall, humidity, wind) plus a
          risk tier — a rough read of how unusual or uncertain conditions are likely to be on that
          date, based on long-term seasonal patterns and warming trends. It is a planning aid for
          understanding climatological tendencies months to years ahead, not a day-specific
          weather forecast.
        

      


      
02 Where the data comes from

      

        

          The dataset covers 8 Indian cities (Mumbai, Bangalore, Jaipur, Delhi, Hyderabad, Kanpur,
          Nagpur, Chhatrapati Sambhajinagar), daily, from 1991 to 2026 — about 105,000 rows. It's
          built from published monthly climate normals per city, expanded into smooth daily values
          with realistic day-to-day variability, seasonal wind patterns, and a long-term warming
          trend layered in, so it behaves like real climate data rather than a flat average.
        

        

          A companion script (scripts/fetch_nasa_power_data.py) can pull the same 7
          cities' real daily data directly from NASA's POWER satellite/reanalysis API, and
          scripts/validate_against_nasa.py checks how closely this project's dataset
          matches that real data, month by month.
        

      


      
03 How a prediction is made

      

        
    
          
  1. Every city/target pair (8 cities × 4 targets = 32 models) has its own trained model.
    2. 
          
  2. The date you pick is converted into a cyclical day-of-year signal (so Dec 31 and Jan 1 are treated as neighbors, not opposites), the year, plus two history-derived features: that day-of-year's long-term seasonal average and a long-term trend value — both computed only from training-period data, so nothing from the test period leaks in.
    3. 
          
  3. Temperature, humidity, and wind speed are predicted with Random Forest regressors.
    4. 
          
  4. Rainfall uses a two-stage model instead: one part estimates the chance it rains at all, another estimates how much if it does — because rainfall is mostly zero with occasional bursts, which a single regressor fits poorly.
    5. 
          
  5. The risk tier blends two things: how far the target date is beyond the models' training cutoff (2018), and how historically volatile that time of year has been for that city.
    6. 
        

      


      
04 Why Random Forest

      

        

          Random Forest wasn't the only option considered. A Historical Baseline (simply
          predicting the day-of-year's long-term seasonal average), Linear Regression, Random
          Forest, and Gradient Boosting were all trained and compared on the same data, features,
          and evaluation split (see scripts/compare_models.py and the Model Analytics
          page).
        

        

          The honest finding: once the historical seasonal average is included as an input
          feature, every candidate model lands within about 0.01–0.05 RMSE of each
          other — for humidity, rainfall, and wind speed, the naive Historical Baseline
          is actually the single best performer by a hair, and Random Forest is close behind. This
          says something real about the problem: for these variables, the seasonal signal already
          explains most of what's predictable, and the added model complexity buys only marginal
          refinement on top of it.
        

        

          Random Forest (and the two-stage rainfall model) stay in production anyway: they still
          edge out the baseline on temperature and capture city-specific nonlinear interactions the
          baseline can't, and they leave room to improve further if better features are added later
          — a fixed baseline can't. The full numeric comparison, per target, is saved in
          models/model_selection.json.
        

      


      
05 Limitations, stated plainly

      

        
    
          
  • This is a climatological outlook, not a weather forecast — no model can reliably predict exact conditions for one specific calendar day more than ~10–14 days out. Treat the output as "what's typical/expected," not "what will happen."
    • 
          
  • Rainfall on any single day remains genuinely hard to predict from date alone (R² ~0.17–0.35) — this is a property of rainfall itself, seen in real meteorological data too, not something a better model architecture fixes. The rain-probability output is more informative than the raw millimeter estimate for this reason.
    • 
          
  • The training data is representative/synthetic by default, built from published climate normals rather than live satellite records — the NASA POWER validation path exists specifically to check and, if you choose, replace this with real data.
    • 
          
  • Risk tiers reflect gradual seasonal instability and long-term trend extrapolation, not discrete extreme events like cyclones or sudden heatwaves.
    •
